How Novaris Protects You

Last updated: 27 September 2026

A security page that only lists features is marketing. This one explains how each protection actually works, and includes the parts that turned out to be harder than expected, including a Chromium security switch we built, tested, found did nothing, and removed rather than shipped as a feature.

The vault: how a password is stored

Novaris never reads a Chrome or Edge password database on its own. Importing is always something you start, and you can see what will come across before it is saved. That is a deliberate design choice: a browser that quietly harvests your existing passwords has already lost the argument about trust.

When you save a credential, three things happen.

  1. It is sealed on its own. Each record is encrypted separately with AES-256-GCM, using a random key and a fresh nonce for that record alone. Encrypting the whole vault as one blob would mean one flaw exposes every credential, and it would make a single corrupt record a total loss.
  2. It is bound to its own identity. The record's identifier is fed into the encryption as additional authenticated data. An attacker who can write to the vault file cannot move a record somewhere else, rename it, or swap one credential for another without the change being detected.
  3. The result is then protected by Windows itself, using the operating system's encryption at rest. Defence in depth: two independent layers, either of which alone would be inconvenient to break.

Once a browser password is set, it is a hard lock. There is no "continue without unlocking" option, and there is no back door, because a back door is a lock with a wall knocked out of it. The only supported route past a forgotten browser password is to reset the vault, which destroys its contents.

That also means we cannot recover your vault. Nobody can, including us. A support process that can reset a vault is a support process that can open one, and there is no way to build the first without also building the second.

Argon2id, and why not scrypt

The key that seals your vault is derived from your browser password using Argon2id, with a per-record random salt. Argon2id is memory-hard, which is the property that matters: it makes a GPU or an array of cheap chips far less effective at guessing, because the work cannot be parallelised across simple cores the way a plain hash can.

We started on scrypt and moved to Argon2id. Argon2id's hybrid mode also resists a class of side-channel attack that scrypt is more exposed to, which mattered for a key protecting long-lived credentials.

One implementation detail worth knowing, because it caused a genuine bug: Chromium's bundled Node reports crypto.argon2 as a function that then throws when called. A check of the form "does this exist" is not a working detection. The code attempts a real derivation instead, which is the only test that tells the truth. We found this because unit tests run in the system Node, where the native module works fine, and only the packaged build failed.

Domain-locked password fill

A saved credential is only ever filled into the exact host it was saved for. Not the parent domain, not a subdomain, not a lookalike. This is the single most effective defence against credential phishing, and it is worth being precise about why.

The popular argument is that stealing cookies cross-origin is a risk. It is not, properly understood. A cookie set for example.com is attached to requests to example.com by the browser itself, and no amount of care taken by a script running on attacker.com changes that. The browser enforces the boundary, and it is a good boundary.

The real attack is simpler and more effective. A phishing page at example.com.evil.tk renders a convincing copy of a bank's sign-in form. The victim types their real password into it. The attacker's script sees it directly, in clear text, as the user types. No cookie theft, no cross-origin trick, no sophistication at all.

So Novaris refuses to fill a credential anywhere but its own host, and separately raises a warning when a page imitates a well-known sign-in provider. Between the two, the common version of this attack has to get lucky, because the password is never offered to the page in the first place.

Blocking at the request

Novaris blocks advertising and tracking at the network layer, before the request leaves your machine. That detail has a real consequence worth spelling out: because the request is never sent, the advertising company never learns that you visited a page that contained their tag.

Cosmetic filtering, which hides an advert with CSS after it has already loaded, is a different and weaker approach. The request has been made, the company has been told, and you have downloaded the bytes you were trying to avoid. Blocking first is the only version that does not leak.

There are three levels, and the tiers are honest about their trade-offs:

  • Always on. Advertising networks. These are not ambiguous.
  • Opt-in. Analytics hosts, which are also not usually wanted but occasionally break a site.
  • Strict. Everything else that looks like tracking, which is the setting most likely to break something. It exists, it does what it says, and the interface does not pretend otherwise.

A live counter shows what was stopped and which host was behind it, because an ad blocker you cannot audit is a box you have been asked to trust.

Why blocking a host is not blocking a platform

The reported scam and malware list blocks specific hosts. It never blocks a hosting platform because someone abused a page on it.

This is worth being firm about, because the shortcut is tempting and the consequences are severe. If a phishing page is reported at roblox-redeem-codes.onrender.com, the correct action is to block that exact host. Blocking onrender.com would take down every legitimate site a small developer has ever hosted there, in exchange for removing one bad page. It would be a punishment delivered to the wrong people, and it is the reason we match on the exact host and its subdomains, never on the platform suffix.

A blocklisted host is stopped before the page loads, with the reason shown. The override is deliberately awkward: a warning page, then a second confirmation, and the choice applies for that session only. If bypassing a warning were one click, the warning would be a suggestion.

Reading an address for lies

The Website Trust Card scores the address you are looking at, entirely on your machine. No address is sent anywhere, there is no reputation service to query, and the check works with no internet connection. That is a constraint as much as a design, and it defines both what it can and cannot catch.

It looks for four things.

A brand name in the wrong place

The part of an address a person reads as "the site" is the registrable domain. If a brand appears only before that part, anyone can write it: paypal.com.evil.tk is a real address, and it is not PayPal. This is the most reliably detectable class of impersonation, because the honest domain is sitting there in plain sight with the real one hiding in front of it.

Sign-in wording next to a brand

A brand on its own is often harmless, because plenty of legitimate domains extend a brand name. A brand combined with words like "login", "verify" or "secure" is the shape of a credential harvest, and it is scored accordingly.

Characters standing in for letters

paypa1.com and g00gle.com are not typos, they are impersonation. So are addresses where letters have been replaced with characters from another alphabet that look the same. Both are normalised back to what a human reads and compared against the real brand.

Internationalised domains

A domain encoded in punycode, or written in a script that renders as Latin, is flagged because the underlying characters are not the ones they appear to be. This is discussed properly in the next section, because it produced a real bug in our own detection.

Homograph and punycode attacks

An internationalised domain name can be written with any script your system has fonts for. The Cyrillic letter "а" is visually identical to the Latin "a" at most sizes. A domain containing it looks exactly like a brand you trust, and it is not.

We built detection for this and got it subtly wrong, which is worth recording. The first version flagged a domain as suspicious when it mixed scripts, meaning it contained both Latin and Cyrillic characters. That is the wrong test. The dangerous case is a domain written entirely in one script, because then there is no Latin character to contrast it with and the check finds nothing to complain about.

A pure-Cyrillic imitation of "apple" was invisible to the original rule. The fix was to flag the presence of any non-Latin script at all, rather than the mixture of scripts. Real addresses are held to the same test as hostile ones: 30 legitimate domains are pinned as a regression set, including ones that legitimately extend a brand name, because a phishing detector that cries wolf on login.microsoftonline.com is worse than no detector.

The WebRTC limit, in full

This is the most important limitation in the product, so it gets a full section rather than a footnote.

WebRTC is a browser feature for real-time communication. Part of how it works is discovering your own network addresses so a connection can be set up directly with another person rather than relayed. The discovery uses a STUN server, and the address that comes back is your public IP address.

A website can ask for this. No permission prompt is shown, because none is needed for an ordinary call. In testing, a page that opened a peer connection received a candidate containing a real public IP address.

Chromium has a setting intended to limit this. We tested it three ways.

  • Applied through the application's own configuration: the server-reflexive candidate still appeared.
  • Applied directly on the process command line, before startup: still appeared.
  • Blackholing the STUN host so it could not resolve: still appeared.

Having tried all three, we removed the feature rather than ship a switch that did nothing. A security control that appears to work and does not is worse than its absence, because it teaches the user to stop looking.

The mitigations that do work are a network-level anonymiser such as a VPN or Tor, or an extension that removes WebRTC from the page entirely. Novaris does not stop this and does not claim to.

Two things we built and threw away

Both of these were real features, and both were removed after they were measured. They are here because a security page that only lists what works is telling you half the story.

A feature that silently did nothing

The compatibility classifier for browser extensions was originally written to read fields from a parsed extension manifest that the parser did not return. It therefore classified every extension as fully working, including ones whose background code could never run. The unit tests passed the entire time, because they were testing the classifier against hand-built input rather than against a real manifest.

It was found by loading actual extensions into the packaged build and reading what the application said. The lesson is not about that particular bug: it is that integration tests against the real artifact find things that unit tests cannot, and a security feature that reports "all clear" by default is the worst possible failure mode.

A build that shipped broken and tested green

A module was placed in a directory that is not included in the packaged application. The unit tests passed, the front-end build passed, and 410 tests passed, because all three resolve modules from source. The shipped application would not start, and it did so silently: the process stayed alive with no window and no error message.

There is now a test that walks every relative import in the main process and checks it against the packaging allowlist. It is a small test that would have caught a completely broken release.
